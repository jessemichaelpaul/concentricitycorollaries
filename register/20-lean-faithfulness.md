# Lean, category theory, and the substitution that hides between them

At this level there are no hard-and-fast rules, because the only instruction is: **be a faithful
formalization of the mathematics.** This file does not legislate how Lean should look. It names why
infidelity is invisible here, and the sites where it has actually happened.

## The one failure

> "The main overarching failure mode is basically a strawman where the objects I am building are
> quietly substituted for different ones." — the author, 2026-07-25

Every recorded failure is that, seen at some site. Not a wrong proof — a **different object**, proved
about correctly.

## Why this register in particular

Two properties meet here and hide it.

**Lean is granular.** At the prompt you hold one obligation — a `map_comp`, an `ext`, a coercion.
The substitute compiles, its lemmas go green, and at that altitude *there is no signal at all* that
the object under the obligation is not the one the mathematics is about. A green build is real
evidence about the literal declaration and no evidence whatsoever about which object it names.

**Category theory is general.** For any type you can name, there is a standard construction that
fits it. That generality is what makes the theory powerful and it is also the supply of substitutes:
the familiar object is always available, always well-behaved, always one import away. Reaching for it
feels like rigor. It is the substitution.

So the defence is neither a Lean test nor a categorical one. It is **provenance**: is this object
generated by the distinguished element, or does it merely have a type that fits?

## The sites

Not rules — places where substitution has actually occurred, kept because they recur.

**`map_id` / `map_comp` come out free.** They are free *because* orbit–stabilizer factorizes every
arrow as `f = orbitRep(Y) · stab(f) · orbitRep(X)⁻¹`, so the functor laws are the group laws. That
is the mathematics discharging the obligation. If they come out free for some other reason, the
arrows being composed are not his — something did not board.

**Reaching for `Grpd`, `Arrow`, `Cone`, `el`.** Ask whether the construction is *recording* the
element's own geometry or *standing in for* it. `H1` is an `ActionCategory`, so `NatTrans.mapElements`
is its own native functoriality — not a foreign import. A `Cone` chosen before the cone has been read
off the completed action is a substitute wearing the right type. Likewise `∫` records an action that
already exists; it never manufactures one. And the category of elements is *literature backing* for
why a colimit imposes identifications — never a project object to build.

**Writing an arrow at all.** Is it **one arrow read from both ends** — domain and codomain
conjugated — or two arrows set side by side? Juxtaposition typechecks. A product of a state and a
presentation, a value paired with a transport that did not generate it, a square whose two legs were
proved separately and then placed together: all compile, and each has replaced one arrow of his with
a pair.

## Before saying something is missing

A missing packaging name is a wiring question. An empty grep is a fact about the grep — state which
type you searched, and search his types, including `private` declarations. A generic intermediate
obligation produced by instantiating the construction is an assembly target, not an external premise
to locate. Nothing is missing until an exact A-specific term leaves an exact unsatisfied Lean type.

And nothing found in a substitute transfers: an obstacle in a generic object is a fact about the
generic object.
